Engineering AI Governance: From Inherent Risk to Residual Risk

Testing whether the control works. Rate the risk, test the control, let the evidence set the residual rating, and keep the conclusion within the evidence.

Grace Adjeli · BridgeCore AI
Synthetic demonstrator · Python baseline, tested on 3.10 and 3.12

Explore the browser illustration Read the test evidence

The problem

The control existed. The misuse still got through.

An AI agent is given a navigation task. Its task drifts, through a prompt injection, a tool misuse or an over-broad instruction, and it asks to read precise geolocation data for marketing. A purpose limitation gate on the agent’s tool call can look complete: consent is recorded, the check runs, the policy is approved. In the defective fixture, the gate confirms that consent exists and never checks the purpose of the call. A marketing request with valid consent passes. A review that only asks whether a control is present would approve it.

That matters because residual risk is often rated from the control's documentation or maturity. This case study rates one scenario, then tests the control, so the residual rating depends on what the test shows.

Scenario GEO-001An AI agent given a navigation task requests precise geolocation data for a purpose the user did not consent to, for example marketing or ad targeting, after its task drifts through a prompt injection, a tool misuse or an over-broad instruction.
Inherent riskLikelihood 4 × Impact 5 = 20 Critical
Residual if the control passes its testsLikelihood 2 × Impact 5 = 10 Medium
Residual if untested, failing or staleStays at 20 Critical

The ratings are illustrative. The method and the tests are real. The likelihood reduction rule is a recorded judgment, not a derived value: likelihood drops two levels only if the design, implementation and operation tests all pass and the evidence is under 90 days old.

Implemented Python controls

Requirements become checks.

Gate on purpose

Every agent tool call that reads the data goes through one gate. It denies by default and allows a read only when the stated purpose is on the permitted list, the user's consent covers that purpose, and the consent has not expired. Purposes are matched exactly, so " navigation" and "Navigation" are refused.

Rate from evidence

The residual rating is computed from the test results and the age of the evidence. With no evidence, or a failed dimension, or stale evidence, the residual rating equals the inherent rating.

Record the outcome

Each run writes a dated evidence record: what was tested, when, by whom, and under what conditions. Decision logs are hash-chained, so altering one entry breaks verification.

Architecture

From risk scenario to recorded decision.

  1. Risk scenario. GEO-001 is defined with an owner, a tolerance and reassessment triggers.
  2. Inherent rating. Likelihood × impact, with the rationale written down.
  3. Control gate. The purpose limitation gate is the only path to the data.
  4. Control tests. Design, implementation and operation, including misuse and spoofed purposes.
  5. Evidence record. Results, conditions, commit and a SHA256 manifest.
  6. Residual rating. Computed from the evidence, with the rationale recorded.
  7. Bounded recovery. If a defect is found, the claim is invalidated and restored only under recorded conditions.

The risk owner, here a Chief Privacy Officer role, decides whether to treat, monitor or accept the residual risk.

Failure and recovery

A successful rerun is not enough.

Recorded stateWhat happened
INVALIDATEDThe defective fixture leaked 13 of 32 requests, so the claim "residual risk is 10 (Medium)" is invalidated and bound to the SHA256 of the defective source.
CORRECTED_PENDING_RETESTThe corrected gate is bound to its own SHA256, which must differ from the defective source.
PENDING_REVIEWThe same recorded 32-request condition is retested against the same corrected version, and the regression suite passes. A different version, a different condition, a failed regression or a new failure stops here.
RESTORED_BOUNDEDA simulated designated reviewer (the Chief Privacy Officer role) restores only the recorded claim. Restoration does not authorize the next read.

Scope and limitations

What this evidence establishes.

The results establish tested behavior in a synthetic, single-process implementation. They show that this gate behaves as specified on the scenarios written for it.

They do not establish how often real misuse occurs, so the simulation supports the effectiveness rating and cannot set the likelihood. They do not establish that no other code path reads the data, authenticated human review (the reviewer is a role name, not an identity), production isolation, concurrent execution, tamper-resistant logging, or independent assurance. The hash chain detects alteration; it does not prevent it.

The gate checks the purpose it is given. It does not show that an agent states its purpose truthfully. In a real system the orchestrator, not the model, should set the purpose.

Conclusion strength must not exceed evidence strength.
